# Browser Bridge Android Loopback Kit, Milestone 2 (Overlay Sheet over Chrome) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add overlay mode to `@bsv/expo-android-wallet-bridge`: when the wallet is warm and unlocked, the launch click raises a translucent `BridgeSheetActivity` over Chrome that shows the existing permission sheets on a second React root of the same React host, and finishes when the user is done.

**Architecture:** M1 (foreground mode) is built and stays the fallback for every cold, locked or unknown state. M2 adds a Kotlin `LifecycleState` (pure) behind a `LifecycleTracker` adapter, a guarded-delegate sheet Activity (S4 findings), a toolbox `ContextRelay` that feeds the second root the first root's contexts, a `sheetOwner()` store that decides which root renders `PermissionSheet`, and attention decisions that read `sheetOwner()` instead of `AppState`. The spikes S3 and S6 run first and can only weaken M2 to the behaviours spec 6.0 allows.

**Tech Stack:** Kotlin (ExpoModulesCore, `react-android` compileOnly), JUnit 4.13.2 (pure JVM), TypeScript, React Native 0.86 / Expo SDK 57, jest, Pixel_9 AVD, adb, uiautomator, puppeteer-core.

**Spec:** `docs/superpowers/specs/2026-10-28-browser-bridge-android-design.md` (revision 4; "spec 7.4" = its section 7.4). Predecessor: `docs/superpowers/plans/2026-10-29-browser-bridge-android-m1.md` (its conventions apply; the commands every task needs are inlined below, so no task has to open M1 to run a check). Evidence of what M1 built and S4 measured: `packages/expo-android-wallet-bridge/SPIKES.md`; scratch code: `packages/expo-android-wallet-bridge/spikes/s4-hello-sheet.diff`.

**Spec values (verbatim)**

- Sheet Activity `org.bsv.walletbridge.BridgeSheetActivity`: `exported="false"`, `launchMode="singleTask"`, `taskAffinity="${applicationId}.bridge"`, `excludeFromRecents`, `windowSoftInputMode="adjustResize"`, no `noHistory`, the `configChanges` list of the S4 diff, theme `@style/Theme.BsvBridgeSheet` (parent `Theme.AppCompat.DayNight.NoActionBar`, `windowIsTranslucent`, transparent `windowBackground`, `windowNoTitle`, `windowCloseOnTouchOutside=false`, `windowAnimationStyle` `@style/Animation.BsvBridgeSheet` with `res/anim/bridge_sheet_enter.xml` (slide up) and `res/anim/bridge_sheet_exit.xml` (slide down), no bar colours; `android:enforceNavigationBarContrast=false` only in `res/values-v29/styles.xml`, because it needs API 29 and minSdk is 24). Main component `BsvBridgeSheet`. Library gradle: `compileOnly 'com.facebook.react:react-android'`. Library manifest declares the normal permission `android.permission.HIDE_OVERLAY_WINDOWS` (needed by `Window.setHideOverlayWindows`).
- Trampoline mode: overlay only when host attached and `ready` and the tracker has caught up and `MainActivity` is alive and not resumed; otherwise `MainActivity` (foreground mode). The sheet gets a sequence number as its only extra (typed `Long`, as `LaunchTrampolineActivity.EXTRA_SEQ` is written); never the URI. A start from a notification tap or `showSheet` carries no sequence number (absent is a valid input, Task 4). Trampoline start throttle stays 3 s.
- Guard: sheet `onDestroy` with `MainActivity` alive calls only `unloadApp()`; not alive (or unknown) calls `super`. Back is native `finish()` (button and `OnBackInvokedCallback`), never `super`, never JS. `onUserLeaveHint` marks left, `onStop` with the mark calls `finish()`; the mark is cleared by `onResume` and `onNewIntent`; a screen-off `onStop` without the mark does not finish. A launch (`onNewIntent` with a new sequence number, or a new `onCreate`) resets the root. `savedInstanceState != null` finishes immediately and re-arms nothing ("arms nothing": the Activity touches no `LaunchStore`, starts no server and posts no notification). The sheet finishes or forwards to `MainActivity` from `onResume` if the tracker reports `MainActivity` resumed (two resumed windows would leave an invisible translucent sheet swallowing touches).
- Protections: `FLAG_SECURE` on every sheet; `Window.setHideOverlayWindows(true)` on API 31+ inside try/catch that fails closed (a `SecurityException` finishes the sheet and forwards to `MainActivity`); drop touches carrying `FLAG_WINDOW_IS_OBSCURED` or `FLAG_WINDOW_IS_PARTIALLY_OBSCURED`, and after `TouchGuard.DROP_LIMIT = 3` dropped touches forward to `MainActivity` (the in-wallet sheet) rather than leaving a prompt the user cannot answer; root keeps `filterTouchesWhenObscured`; scrim about 90 percent; Approve tap protection `TAP_PROTECTION_MS = 700` (existing in `PermissionSheet`). The sheet window is non-touchable (`FLAG_NOT_TOUCHABLE`) and paints no scrim while nothing is pending.
- `sheetOwner()` returns `'main' | 'overlay' | 'none'`: `'overlay'` iff the sheet is resumed and `MainActivity` is not; `'main'` iff `MainActivity` is resumed. Every attention decision and the foreground-mode `returnToBrowser` gate use it, never `AppState`, with one exception: while the tracker is not registered (`registered` false, before about 1.8 s after a cold start), `sheetOwner()` falls back to `AppState === 'active' ? 'main' : 'none'` so M1 foreground mode keeps its semantics. `AppState` goes `background` then `active` about 50 ms apart at each handover, and `sheetOwner()` is briefly `'none'` at each Main-to-sheet or sheet-to-Main handover (no Activity is resumed): nothing closes a binding, fails or answers a request, or locks on `background`, and any decision acting on owner `'none'` or on `background` waits at least 500 ms and re-reads state.
- `RELAYED_CONTEXTS` names the toolbox `ThemeContext` (`core/theme/ThemeContext.tsx`), `WalletContext` (`core/context/WalletContext.tsx`), `ExchangeRateContext` (`core/context/ExchangeRateContext.tsx`) and `UserContext` (`core/context/UserContext.tsx`). Test ids: `bridge-sheet-root` (overlay root, new), `bridge-approve`, `bridge-deny`, `bridge-connect-origin` (exist since M1).
- Notifications still name no site. A notification tap `PendingIntent` always targets `BridgeSheetActivity` (explicit component, `FLAG_IMMUTABLE`); the Activity decides before `super.onCreate` (Task 6): mode `OVERLAY` shows the sheet, mode `FOREGROUND` forwards to `MainActivity` and finishes without loading React, leaving `raisedByBridge` false (a notification-raised wallet is deliberately not sent back, SPIKES case 16).
- Logs (O13 no-secrets rule): the only M2 log lines are tag `BsvBridgeSheet` with counts, never values: `sheet-activity create n=<n> seq=<seq-or-none>`, `sheet-activity newintent reset=<bool>`, `sheet-root mount n=<n>` (JS, count only).

## Review Focus

Inputs the spec implies but its M2 test list does not name; each has a test in the named task.

1. Screen turns off while the sheet is up: `onStop` without `onUserLeaveHint` must not finish it, and waking resumes the same root with the same pending prompt; a leave that returns (recents peek) then a screen-off must not finish it either (Task 4 `screen-off stop without leave mark does not finish`, `leave then resume then stop does not finish`, Task 13 case O7).
2. OS task restore or process recreation (`savedInstanceState != null`) must finish at once and arm nothing (Task 4 `onCreateAction restored state is FINISH`, Task 13 case O18 `am crash` with the sheet up: no sheet resumed, no listener on the bridge port, no `LaunchStore` read in logcat).
3. A stale `onNewIntent` (same or older sequence number than the root already shows, or no sequence number at all) must not reset a root that is showing a pending prompt (Task 4 `stale sequence does not reset`, `absent sequence does not reset a shown root`; the replace-then-read bug of `onNewIntent` is caught on a device by Task 13 case O10).
4. The user switches light or dark while the sheet is up: the sheet re-themes through the relay without remounting (Task 8 `theme change reaches the subscriber without remount`, Task 13 case O9 `adb shell cmd uimode night yes`).
5. `returnToBrowser` after the sheet already finished (a Back race), or with no sheet and no raised main: a no-op, never `ERR_NO_ACTIVITY` to JS (Task 4 `ReturnPolicy.decide` NONE rows, Task 10 `returnToBrowser after Back is a no-op` over a fake native, Task 13 case O19 Back 300 ms after the last Approve).
6. The two M1 fixes that act on `AppState` transitions (F1 `ddbba5e1`: an approved grant is answered at once when the app leaves the foreground, because the 400 ms JS timer pauses when stopped (S5b); the `Sheet` re-apply of its open position on `active`) meet the 50 ms handover blip: the blip must neither hide the sheet nor lose or duplicate an approved grant (Task 10 `blip neither hides the sheet nor loses or duplicates an approved grant`). F1 is never debounced in JS (JS timers do not fire while stopped).
7. Owner flips twice in one tick pair (two roots subscribed to one store): `PermissionSheet` is never mounted twice, even transiently (Task 9 `max concurrent PermissionSheet is 1 under both subscription orders`).
